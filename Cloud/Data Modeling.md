**Моделирование данных** — это способ показать, где и как хранятся данные в системе, и как они связаны.

**Данные** — это сырые факты, числа, картинки, которые сами по себе не несут смысла.

**Информация** — это обработанные данные, которые помогают принимать решения. Чтобы получить полезную информацию, нужно правильно собирать, хранить и анализировать данные.

Данные становятся информацией после обработки.

Чтобы достичь максимальной бизнес-ценности для заинтересованных сторон, вам необходимо понимать, какие данные у вас есть и как их хранить.

Используйте нереляционную базу данных для потоковых процессов и обработки данных на ходу.

Используйте реляционные базы данных для аналитических платформ и построения диаграмм.

Ключевое преимущество моделирования данных заключается в том, что вы тщательно исследуете свои данные и определяете наилучший способ работы с ними, что позволяет вам обрабатывать данные более эффективно.



 	Уровни моделирования данных

1\\ Концептуальный уровень (для бизнеса) - определяет, какие данные нужны и как они связаны. Описание типов сущностей, связей и ограничений.

2\\ Логический уровень (для аналитиков и архитекторов) - описывает структуру данных для выбранной базы данных (например, какие таблицы и связи).

3\\ Физический уровень (для разработчиков) - описывает, как данные реально будут храниться в базе (типы данных, индексы, таблицы).

Conceptual (Entity Names, Entity Relationships)

Logical (Entity Relationships, Attributes, PK, FK)

Physical (PK, FK, Table Names, Column Names, Column Data Types)



&nbsp;	Техники моделирования данных

1\\ ER-моделирование (сущность-связь) - показывает, какие объекты (сущности) есть в системе и как они связаны. Пр: "Продукт" ==(связь)==>  "Модель продукта"

2\\ 3NF (третья нормальная форма) - помогает убрать повторяющиеся данные и сделать хранение данных логичным. Подвид ER-моделирования.

Добавляет атрибуты (свойства сущностей) и ключи (уникальные идентификаторы). Ключи бывают составные, естественные и суррогатные.

Используется в  ERP и CRM.

3\\ Многомерное (dimensional) моделирование - денормализованная модель 3NF, оптимизированная для отчеов и анализа. Использует факты, измерения и меры.

3а\\ Факт — главная таблица с основными данными (пр: продажи).

**Таблица фактов** хранит числовые значения (факты) и ФК на таблицы измерений.

Виды таблиц фактов:

а\\ Транзакционные: хранят отдельные события (пр: покупки, звонки).

б\\ Накопительные: хранят суммированные значения за период (пр: итоговые продажи за месяц).

в\\ Периодические: хранят снимки состояния на определённую дату (пр: остаток на счёте).

г\\ Безфактовые: содержат только ключи измерений, без числовых данных.

**Факты** — это числа, которые описывают бизнес-процесс (пр: сумма продажи).

Виды фактов:

а\\ Аддитивные: можно складывать по любым измерениям (пр: сумму продаж).

б\\ Неаддитивные: нельзя складывать (пр: проценты).

в\\ Полуаддитивные: можно складывать только по некоторым измерениям (пр: баланс по клиенту, но не по датам).

**Детализация** — это уровень, на котором хранятся факты (день, месяц, год). Чем выше детализация, тем точнее данные, но больше места нужно для хранения.

3б\\ Измерения — таблицы с описанием данных (пр: дата, товар, магазин). Структура, которая классифицирует факты и меры, позволяя пользователям отвечать на бизнес-вопросы. Редко изменяются. Связаны с таблицей фактов по принципу "один ко многим". Таблицы измерений выполняют три основные функции: фильтрация, группировка, маркировка.

Для построения зависимостей между измерениями создаётся иерархия.

Типы измерений (в зависимости от типов данных внутри них):

Соответствующее — используется в нескольких фактах (например, дата).

Ненужное — для случайных атрибутов.

Вырожденное — только ключ, без атрибутов (пр: номер заказа).

Ролевое — одно измерение с разными ролями (пр: OrderDate, ShipDate или CloseDate).

3в\\ Меры — числовые значения в таблице фактов (пр: сумма продаж).

4\\ Другие методы моделирования: Data Vault, Anchor и т. д. 



&nbsp;	Построение модели 3НФ (для OLTP)

3NF моделирование: Подходит для хранения рабочих (оперативных) данных, например, в ERP и CRM. Быстро работает с простыми запросами. Используется для обычных операций: добавление, изменение, удаление данных. Хорош для транзакций (OLTP).

**Нормализация** данных (дробление таблиц) - уменьшить дублирование, избежать аномалий, обеспечить ссылочную целостность и упростить управление данными. Для уменьшения избыточности данных и повышения их целостности.

1NF: Все значения в ячейках атомарные. Нет одинаковых строк.

2NF: Нет частичных зависимостей от части составного ключа.

3NF: Нет косвенных (транзитивных) зависимостей. Все данные зависят только от ключа.



&nbsp;	Построение многомерной модели (для OLAP)

Многомерное моделирование: Подходит для анализа и отчетов, когда нужно объединять данные из разных источников. Удобно для сложных аналитических запросов и хранения истории. Обычно содержит меньше таблиц, данные часто денормализованы. Хорош для аналитики (OLAP).

Есть два типа схем:

Звезда (работает быстрее) — простая, все измерения связаны напрямую с таблицей фактов.

Снежинка — более сложная, измерения могут быть связаны друг с другом.

4 шага построения:

1\\ Выбрать бизнес-процесс (что анализируем, пр: продажи).

2\\ Определить уровень детализации (пр: продажи по дням и магазинам).

3\\ Определить измерения (пр: продукт, дата, магазин).

4\\ Определить факты (пр: сумма продаж).

&nbsp;	Медленно изменяющиеся измерения (**SCD**):

Иногда изменения изменений (меняются редно) нужно отслеживать для истории:

Типы SCD:

Тип 0: Значения не меняются, только добавляются новые строки. История не хранится. ПР: дата рождения, страна.

Тип 1: Старое значение просто заменяется новым. История не хранится. ПР: изменили имя клиента — старое имя исчезло.

Тип 2: При изменении создаётся новая строка с новыми датами (StartDate, EndDate, IsCurrent). История сохраняется. 

Тип 3: Добавляется новый столбец для хранения предыдущего значения. Хранятся только два значения: текущее и предыдущее. ПР: есть столбец "старый адрес" и "текущий адрес".

Тип 4: Есть отдельная историческая таблица, где хранятся все изменения. Основная таблица содержит только текущие значения. ПР: основная таблица — текущий адрес, историческая — все прошлые адреса.

Тип 6: Комбинация типов 1, 2 и 3. В одной таблице хранятся все состояния: текущее, предыдущее, даты начала и конца, флаг текущего.

&nbsp;	**Data Factory**

**Data Factory** — это платформа для работы с данными: хранения, обработки, анализа и моделирования.

Платформа анализа данных: Помогает собирать, хранить и анализировать данные из разных источников; Главная цель — превращать данные в полезную информацию для бизнеса.

&nbsp;	Архитектуры обработки данных:

Lambda: Два слоя — пакетная обработка (исторические данные) и потоковая обработка (в реальном времени). Гибко, но сложно.

Kappa: Только потоковая обработка для всех данных. Проще, но не всегда подходит для сложной пакетной обработки.

&nbsp;	**Эталонная архитектура** **EPAM Data Factory** включает уровни:

1\\ Streaming/Batch Data Sources (откуда берутся данные)

2\\ Edge/Ingestion - Автоматическое извлечение (из сорса) и загрузка данных (в таргет с-му)

3\\ Data Storage - долговременное хранения больших объемов данных.

4\\ Analytics Production Pipelines - Обработка и преобразование данных (ETL)

5\\ Management Components — каталоги данных, модели данных и мониторинг/планирование джоб.

6\\ Data and ML Exploratory Environment - набор тулов для проведения интеллектуального анализа данных и статистического анализа.

7\\ Data Produts - гибкое хранилище для готовых данных и сервисов. 

8\\ Access Layer — интерфейсы, ориентированные на конечного пользователя, которые предоставляют доступ к опубликованным данным и продуктам ИИ.

Особенности слоев: каждый слой может разрабатываться и поддерживаться индивидуально; архитектура полностью независима от поставщиков/сервисов.



**Data Source** — это данные, которые поступают из внутренней или внешней системы (пр: таблица из базы, файл, поток сообщений). Его нужно обработать, чтобы получить ценность.

**Этапы Data Source:**

1\\ Извлечение из исходной системы — получаем данные из исходной системы (файлы, таблицы, события).

2\\ Доставка на платформу — может быть постоянно или по расписанию.

3\\ Загрузка на платформу - загружает новые данные в систему и оптимизирует их для дальнейшего использования.

4\\ Качество данных - проверяем данные на ошибки и соответствие правилам.

5\\ Происхождение данных (Data Lineage) - отслеживаем путь данных от источника до хранения. Выявляет любые потенциальные аномалии и запрашивает повторную передачу данных для затронутого диапазона.

6\\ Retention Policy - определяем, как долго храним данные, исходя из законов и стоимости.



**Data Product** — это обработанные данные, которые приносят пользу бизнесу (пр: отчёт, панель с показателями). ПР: Бизнес-панель с KPI; Ежедневный финансовый отчёт. Продукты данных создаются для конкретных целей, они управляются как ПО: версионируются, тестируются, улучшаются и устаревают. 

**Этапы Data Product:**

1\\ Определение задачи — выясняем, какую бизнес-проблему нужно решить.

2\\ Иследование —  профилирование данных, анализ исходных систем и сопоставление с потребностями бизнес-проблемы.

3\\ Итеративный процесс разработки — создаём прототип, тестируем с пользователями.

4\\ Оценка результатов — проверяем, насколько продукт полезен.

5\\ Внедрение продукта данных в производство — запускаем продукт в работу, настраиваем управление и качество.

6\\ Процесс выпуска —  регистрация и версионирование продукта данных, процес тестирования и UAT.

7\\ Процесс внедрения (adoption) — собираем обратную связь, улучшаем продукт.

**Этапы разработки Data Product:**

1\\ Исследование и проектирование — определяем, что нужно бизнесу, ищем данные, делаем прототип.

2\\ Сбор и хранение данных — загружаем нужные данные.

3\\ Доставка данных — настраиваем, как продукт будет доступен пользователям.

4\\ Производственный конвейер — автоматизируем обработку, управление планированием, мониторингом и потоком.
